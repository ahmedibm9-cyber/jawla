# Flexible RBAC with Filament Shield — Implementation Plan

> **For Claude:** Use `@skills/collaboration/executing-plans/SKILL.md` to implement this plan task-by-task.

**Goal:** Replace hardcoded `hasRole()` checks with flexible permission-based checks using Filament Shield, so admin can create/manage roles and assign permissions through a UI.

**Architecture:** Install Filament Shield (which wraps spatie/laravel-permission), generate permissions for all Filament resources/pages/widgets, update all 23 policies to use `can()` instead of `hasRole()`, and update navigation/widget visibility to be permission-based.

**Tech Stack:** Laravel 12, Filament 4, spatie/laravel-permission (already installed), bezhansalleh/filament-shield (to install)

---

## Current State Summary

- **23 policies** with ~50 `hasRole()` / `hasAnyRole()` calls
- **4 Filament pages** with `can()` or `hasRole()` access checks
- **3 Filament resources** with `hasRole()` visibility checks
- **10+ Service classes** with `hasRole()` business logic checks
- **RoleSeeder** already defines 50+ Spatie permissions and maps them to 10 roles
- `spatie/laravel-permission` installed, `HasRoles` trait on User model
- `filament-shield` NOT installed

## Key Decision: What Changes vs. What Stays

**Changes:**

- Policies: `hasRole('admin')` → `can('invoice_delete')` (permission-based)
- Navigation: role-based → permission-based
- Widget visibility: role-based → permission-based

**Stays the same:**

- `isSuperAdmin()` method — kept as superadmin bypass
- `canAccessPanel()` — kept role-based (high-level panel gate)
- Service classes — business logic role checks stay (they validate workflow actors, not UI access)
- Rep panel (`/app/*`) — completely separate, untouched
- RoleSeeder — updated to align with Shield's generated permissions

```php
<?php

namespace App\Policies;

use App\Models\User;

class UserPolicy
{
    public function viewAny(User $u): bool
    {
        return $u->can('user_view_any');
    }

    public function view(User $u, User $target): bool
    {
        if ($u->isSuperAdmin()) {
            return true;
        }

        return $u->can('user_view') && ! $target->isSuperAdmin();
    }

    public function create(User $u): bool
    {
        return $u->can('user_create');
    }

    public function update(User $u, User $target): bool
    {
        if ($u->isSuperAdmin()) {
            return true;
        }

        return $u->can('user_update') && ! $target->isSuperAdmin();
    }

    public function delete(User $u, User $target): bool
    {
        if ($u->isSuperAdmin()) {
            return true;
        }

        return $u->can('user_delete') && ! $target->isSuperAdmin();
    }
}
```

## Risk Mitigation

2. **Permission explosion** — Shield generates ~180 permissions. This is fine — Spatie caches them.
3. **Performance** — No change. Spatie permission checks are cached.
4. **Rollback** — If something breaks, revert policies to `hasRole()` checks. Shield installation is additive.
