# Jawla Build Guide — Final Supplement

**Purpose:** Address the 5 gaps identified after the stress test. Three
strengthen existing findings (ADR, capability ownership, AI session
protocol); two are genuinely new (architectural invariants, extension
points).

Also incorporates feedback on over-documentation: notification channels
trimmed to interface + database only; Filament conventions trimmed to
naming + ownership + folder; middleware trimmed to project-specific only.

# NEW FINDING 1 — System Invariants (Non-Negotiable Rules)

## Problem
The guide has business rules (§7), coding rules (CLAUDE.md), and
engineering rules. But it does not have **system laws** — truths that
hold regardless of which phase, which service, which feature. When an AI
agent encounters an ambiguous situation (e.g., "should I update
`stocks.quantity` directly in this seeder?"), it has no anchor. It
guesses. If the guess violates an invariant, the system is silently
broken.

Invariants are different from coding standards. Standards say *how* to
write code. Invariants say *what the system must always be true*.

## Why this matters
An AI agent building Phase 17 (data migration) may write
`Stock::where('product_id', $id)->update(['quantity' => 100])` in the
migration seeder — bypassing StockService, no movement row, no audit.
This violates "stock only changes through StockService" but the agent
doesn't know that's an invariant because it's buried in CLAUDE.md as a
coding rule, not elevated to a system law.

Invariants are the **first thing the AI reads** when it's unsure. They
override every other instruction. If a phase task contradicts an
invariant, the invariant wins and the agent raises an ADR.

## Exact location
New section **§0.6 System Invariants**, immediately after §0.5 (AI
context management). This is the highest-priority section — read before
any phase, before any business rule, before any coding standard.

## Paste-ready text

```markdown
### 0.6 System Invariants (non-negotiable system laws)

These invariants hold for every phase, every service, every line of
code. If any instruction in this guide, in docs/, or in a phase task
contradicts an invariant, **the invariant wins**. The agent must raise
an ADR (§0.3) documenting the conflict before proceeding.

No invariant is ever relaxed without an ADR explicitly marked
"INVARIANT EXCEPTION" and approved by the user.

#### Inventory invariants
1. **Stock changes only through StockService.** No code outside
   `StockService` and its implementations may write to `stocks.quantity`
   or `stock_movements`. This includes seeders, migrations, tinker,
   queue jobs, and Artisan commands. The only exception is
   `StockReconciliationService` which calls `StockService::reconcile()`.
2. **Every stock change writes a movement row in the same transaction.**
   No movement row = no quantity change. No exception.
3. **Stock never goes negative.** Enforced at service layer
   (bilingual error) AND at DB level (`CHECK (quantity >= 0)`).
4. **Van stock is decremented at sale time, not at proforma time.**
   Proformas do not reserve stock.

#### Financial invariants
5. **All money mutations run inside `DB::transaction()`.** Invoice,
   payment, return, expense, cash box, van transfer, landed cost
   distribution — all wrapped. No exception. If a controller or
   Livewire component calls `Model::create()` or `Model::update()` on a
   money column, that is a bug.
6. **Money arithmetic uses bcmath (string operands), never float.**
   `bcadd`, `bcmul`, `bcdiv`, `bccomp` with explicit scale. The `Money`
   value object (§11.52) enforces this.
7. **Reversal is compensating, never destructive.** A cancelled invoice
   gets a reverse `stock_movements` row (negative qty, reason=
   `adjustment`), not a `DELETE`. The original row stays. The
   cancellation is itself logged in `activity_log`.
8. **Balances are computed, not stored directly.** `customer.balance`
   and `cash_boxes.balance` are updated by the service that caused the
   change, inside the same transaction. They are never edited via
   Filament or Livewire forms. The aging report recomputes from
   invoices + returns + payments to verify.
9. **Cost price is never exposed to sales roles.** Not in API responses,
   not in Blade output, not in JSON payloads, not in exports, not in
   logs, not in Filament forms visible to reps or sales managers. The
   `products.cost` column is hidden via API resource serialization,
   Filament field visibility, and a `Gates` check.

#### Document invariants
10. **Invoice numbers are sequential, server-generated, immutable, and
    gapless.** Generated by `DocumentNumberService` with row-level
    locking. Never client-generated. Never editable after issuance.
    Cancelled numbers are skipped (not reused).
11. **Submitted documents are immutable.** An invoice with
    `status='submitted'` cannot have its items, prices, or totals
    edited. Correction = cancel + amend (§11.30). The `amended_from`
    link preserves the chain.
12. **Every transactional document has `posting_date`.** Reports filter
    by `posting_date`, never by `created_at`. `posting_date` is the
    Egypt business date at the time of posting (§11.32, M-3).
13. **Compliance identifiers (ETA UUID, ZATCA QR, invoice number) are
    immutable once issued.** They may not be regenerated, edited, or
    reused. A correction creates a new document with a new identifier
    linked to the old via `referenceOldUUID` (ETA) or `amended_from`
    (internal).

#### Tenant invariants
14. **Every query on a `company_id`-bearing table is company-scoped.**
    The `BelongsToCompany` global scope (§4.0) enforces this. The only
    bypass is `Model::withoutGlobalScope('company', ...)` inside an
    admin-only code path, wrapped in an explicit `where('company_id',
    $id)`.
15. **A rep never sees another rep's data.** `user_id` filter on
    visits, invoices, payments, returns, expenses, work sessions.
    Enforced by Policy (H-4), not by UI hiding.

#### Audit invariants
16. **Every mutation of a transactional document writes to
    `activity_log`.** Who, what, when, before/after. Via
    `spatie/laravel-activitylog` called by the service, never by the
    controller.
17. **`stock_movements` is append-only.** No `UPDATE`, no `DELETE` on
    this table. Corrections are new rows with negative `quantity_change`
    and `reason='adjustment'`. This is enforced by a DB trigger that
    blocks UPDATE and DELETE.
18. **Security-relevant events are logged.** Failed logins, role
    changes, permission grants, exports, impersonation, stock
    adjustments, price changes — all in `activity_log` with
    `action='security_*'`.

#### Architectural invariants
19. **Business logic never resides in controllers, Filament resources,
    or Livewire components.** They call services. Services contain
    business logic. Controllers/components contain HTTP handling, form
    mapping, and response formatting. If a controller has an `if`
    statement that's not about HTTP status, it belongs in a service.
20. **Services depend on interfaces, not implementations.** Every
    service is bound to its interface in a ServiceProvider. Controllers
    and Livewire type-hint the interface. This makes every service
    mockable in tests.
21. **Cross-cutting side effects use domain events, not inline calls.**
    A service does the core mutation, then dispatches an event.
    Listeners handle alarms, notifications, logs, PDFs. The service
    does not know about alarms.
22. **No shell execution.** `exec`, `shell_exec`, `system`, `passthru`,
    `proc_open`, `eval` are forbidden. No user input reaches a command
    line. (Already in CLAUDE.md — elevated to invariant.)
23. **No secrets in code, logs, Blade, JS bundles, or client responses.
    Only `.env`.** (Already in CLAUDE.md — elevated to invariant.)
24. **Every destructive or financial action requires a bilingual
    confirmation modal stating the exact consequence.** (Already in
    CLAUDE.md — elevated to invariant.)

#### Enforcement
- **In code:** PHPStan rules (custom ruleset) check that no controller
  calls `Stock::update()` or `Invoice::create()` directly. These are
  static-analysis guards, not just conventions.
- **In tests:** `InvariantTest.php` runs on every CI build and asserts
  each invariant with a targeted test (e.g., "attempt direct
  `stocks.quantity` update throws", "attempt to read cost price as rep
  returns 403", "cancel invoice creates reverse movement, original
  unchanged").
- **In review:** the AI agent checks every diff against this list
  before committing. If a change violates an invariant, the agent
  stops and raises an ADR.
```

# NEW FINDING 2 — Extension Points

## Problem
The guide defines what to build but never defines **where future
features plug in**. When a future AI session needs to add "WhatsApp
invoice sending" (deferred to v2 per §10), it doesn't know whether to:
- Add a new notification channel?
- Add a new listener on `InvoiceSubmitted`?
- Modify `InvoiceService::submit()`?
- Create a new `WhatsAppService`?

Without extension points, the agent modifies core code, creating
coupling and regression risk. Extension points tell the agent: "here is
where you add X, here is what you must NOT touch, here is the interface
you implement."

## Why this matters
ERPNext has survived 15 years because its extension points (hooks,
overrides, custom fields) are well-defined. Without them, every
customization forks the core. An AI agent without extension-point
guidance will patch `InvoiceService::create()` to add WhatsApp sending,
breaking the sale flow when the WhatsApp API is down.

## Exact location
New subsection **§11.76 Extension points**.

## Paste-ready text

```markdown
### 11.76 Extension points (where future features plug in)

Every subsystem defines its extension points. A future AI session
adding a feature uses the extension point, NOT a modification to core
code.

#### Notification system
| Extension point | Interface | How to extend | Forbidden |
|---|---|---|---|
| New channel (email, SMS, WhatsApp, push) | `NotificationChannel` interface with `send($notifiable, $notification): void` | Implement the interface, register in `NotificationServiceProvider`, add to the notification's `via()` method | Modifying `NotificationService::send()` core logic |
| New notification type | Create a class extending `DatabaseNotification` | Add `toDatabase()` returning bilingual title + body + link | Dispatching notifications directly from a service (use `NotificationService::send()` which respects user preferences) |

**Allowed:** adding a new channel class + registering it.
**Forbidden:** editing `NotificationService` to hardcode a new channel.

#### Pricing system
| Extension point | Interface | How to extend | Forbidden |
|---|---|---|---|
| New pricing rule (tier, customer-specific, seasonal) | `PriceRule` interface with `apply(PriceCalculation $calc): PriceCalculation` | Implement, register in `PricingServiceProvider`, add to the pricing pipeline | Modifying `PricingService::priceForRep()` core logic |
| New discount type | `DiscountStrategy` interface | Implement, register, add to the discount pipeline | Hardcoding discount math in `InvoiceService` |

**Allowed:** adding a new `PriceRule` implementation.
**Forbidden:** editing `PricingService` to add a new `if` branch.

#### Stock operations
| Extension point | Interface | How to extend | Forbidden |
|---|---|---|---|
| New stock movement reason | Add enum case to `MovementReason` + handle in `StockService::decrement/increment` switch | Add the enum case, add the reason to the switch, write the test | Creating a new service that writes to `stocks` or `stock_movements` directly |
| New warehouse type (e.g., 'consignment') | Add enum case to `WarehouseType` + handle in scope/filter logic | Add enum, add scope, add Filament filter | Bypassing the `BelongsToCompany` scope on warehouse queries |

**Allowed:** adding a `MovementReason` enum case.
**Forbidden:** creating a `StockAdjustmentService` that writes to
`stocks.quantity` without going through `StockService`.

#### E-invoicing
| Extension point | Interface | How to extend | Forbidden |
|---|---|---|---|
| New country e-invoicing (ZATCA, UAE FTA, etc.) | `EInvoicingStrategy` interface with `submit(Invoice $i): string`, `cancel(Invoice $i): string`, `generateQr(Invoice $i): string` | Implement the interface, register per company country, add to `EInvoicingService` strategy resolver | Modifying `EtaIntegrationService` to add ZATCA branches |
| New QR format | `QrStrategy` interface with `encode(Invoice $i): string` | Implement, register per company, add to `PdfService` | Hardcoding QR generation in the PDF Blade template |

**Allowed:** adding a `ZatcaEInvoicingStrategy` implementing
`EInvoicingStrategy`.
**Forbidden:** adding `if ($company->country === 'SA')` branches inside
`EtaIntegrationService`.

#### Reports
| Extension point | Interface | How to extend | Forbidden |
|---|---|---|---|
| New report | Create a class extending `BaseReport` with `data(): array`, `columns(): array`, `export(): StreamedResponse` | Implement, register in `ReportServiceProvider`, add a Filament page | Writing report queries in Filament resources or Livewire components |
| New dashboard widget | Create a Filament Widget class extending `ChartWidget` or `StatsOverviewWidget` | Implement `getHeading()`, `getData()`, register in the Dashboard | Modifying the Dashboard class to add inline widgets |

**Allowed:** adding a `MonthlySalesReport` class + Filament page.
**Forbidden:** writing a 200-line query in a Livewire component.

#### Data import
| Extension point | Interface | How to extend | Forbidden |
|---|---|---|---|
| New import source (not Odoo/Excel) | `ImportSource` interface with `read(): LazyCollection` | Implement, register, add to `DataMigrationService` | Writing import logic in an Artisan command body |
| New import target (new table) | `ImportTarget` interface with `write(LazyCollection $rows): ImportResult` | Implement, register | Writing `Model::insert()` in the Artisan command |

#### Visit workflow
| Extension point | Interface | How to extend | Forbidden |
|---|---|---|---|
| New visit purpose | Add enum case to `VisitPurpose` + handle in `VisitService::open()` | Add enum, add handling, write test | Creating a separate `VisitServiceV2` |
| New visit report field | Add column to `visit_reports`, add to Form Request, add to Livewire form | Migration + form update + test | Creating a separate `VisitReportExtended` model |

#### General rules for extension points
1. **If you're adding a new `if` branch to an existing service method,
   stop.** That's a new strategy/rule. Extract an interface, implement
   the new path as a separate class, register it.
2. **If you're modifying a core service's method signature to add a
   parameter, stop.** That's a breaking change. Use a DTO or a strategy
   pattern instead.
3. **If you're creating a second service that does what an existing
   service does plus one more thing, stop.** Extend the existing
   service via its extension point.
4. **Every extension point has a test.** The test verifies the
   interface contract: the new implementation produces the same shape
   of output as the existing ones.
5. **Every extension point is documented in an ADR** (§0.3) explaining
   why the extension was needed and what interface was chosen.
```

# STRENGTHENED FINDING 1 — ADR (was M-AI-3, now stronger)

## User feedback
"Still missing. Huge. Every enterprise project eventually asks: why did
we do it this way?"

My earlier version listed 10 seed ADRs but didn't say when to create
new ones, how to number them, or how to link them to the code. The user
is right — it was a stub, not a protocol.

## Strengthened paste-ready text

```markdown
### 0.3 Architecture Decision Records (ADR)

#### Format
Every ADR is a file in `docs/adr/NNNN-kebab-case-title.md`:

```markdown
# ADR-NNNN: {Decision title}

## Status
Proposed | Accepted | Superseded by ADR-XXXX | Deprecated

## Date
YYYY-MM-DD

## Phase
Phase N (the phase that triggered this decision)

## Decision
One sentence. What we decided.

## Context
Why this came up. What problem we're solving. What constraint we're
under.

## Alternatives considered
- Alternative A — why we didn't choose it.
- Alternative B — why we didn't choose it.
- Alternative C — why we didn't choose it.

## Chosen approach
What we picked. How it's implemented (one paragraph or a code snippet).

## Consequences
What we accept by choosing this:
- Positive: what we gain.
- Negative: what we lose or risk.
- Neutral: what's unchanged but worth noting.

## Related
- ADR-XXXX (if related)
- §X.X of the build guide (the section this decision affects)
- The invariant this decision respects or exceptions (§0.6)
```

#### When to create an ADR
Create an ADR when ANY of the following happen:
1. **You chose between two or more viable approaches.** If there was
   only one way, no ADR needed.
2. **You added a new package** not in §2.
3. **You relaxed or exceptioned a system invariant** (§0.6). The ADR
   must be titled "INVARIANT EXCEPTION: {invariant number}" and requires
   user approval before the code is merged.
4. **You made a non-obvious database design decision** (e.g., chose
   partial unique index over a trigger, chose partitioning strategy).
5. **You introduced a new architectural pattern** (e.g., decided to use
   a Repository for one service despite §11.60 saying YAGNI).
6. **You deviated from the guide.** The ADR explains why the guide's
   instruction was wrong or impractical for this specific case.

#### When NOT to create an ADR
- You followed the guide exactly.
- You chose between a named function and an anonymous function.
- You chose a variable name.
- You chose which test to write first.

#### Numbering
- Sequential, zero-padded, starting at 0001.
- Never reused. Superseded ADRs keep their number.
- The ADR's number is referenced in code comments where relevant:
  `// See ADR-0007 for why Egypt ETA uses URL-format QR`.

#### Seed ADRs (create in Phase 0, before any feature work)
1. ADR-0001: PostgreSQL over MySQL (transactions, partitions, partial
   indexes, CHECK constraints).
2. ADR-0002: Filament for admin, Livewire for rep app (one codebase,
   no API layer, no SPA).
3. ADR-0003: Service layer with interfaces (no Eloquent in controllers
   for money/stock).
4. ADR-0004: Exclusive VAT in v1 (inclusive deferred to v2 per §7
   rule 24).
5. ADR-0005: Moving average valuation (simplest for trading, real-time
   on receipt).
6. ADR-0006: Egypt ETA = full API integration with URL-format QR (not
   TLV, not JSON — verified against sdk.invoicing.eta.gov.eg).
7. ADR-0007: ZATCA Phase 1 = TLV Base64 QR, 5 fields, no API (deferred
   to v2, structure stored in `zatca_qr` field).
8. ADR-0008: Cancel-not-delete for transactions (audit trail
   preservation per §11.44).
9. ADR-0009: Global company scope via trait + middleware (multi-
   tenancy enforcement per §4.0).
10. ADR-0010: Domain events for cross-cutting side effects (alarms,
    notifications, logs decoupled from core mutations).
11. ADR-0011: `stock_movements` partitioned by month (range partition
    on `posting_date`).
12. ADR-0012: bcmath for all money arithmetic (never float).

#### Review protocol
- At each phase boundary, review ADRs created during the phase.
- If an ADR supersedes an earlier one, update the earlier ADR's status
  to "Superseded by ADR-XXXX" and create the new one.
- ADRs are committed to git like any other file. The commit message:
  `docs: ADR-NNNN {title}`.
```

# STRENGTHENED FINDING 2 — Capability Ownership (was M-AI-2)

## User feedback
"I still don't see: Pricing → PricingService, DiscountService,
PriceRuleRepository, PricingPolicy, Pricing Events. Every capability
should have one owner."

My earlier version was a flat table of 30 services. The user wants a
**capability hierarchy** — not just "PricingService owns pricing" but
the sub-capabilities within pricing, who owns each, and what the
dependency graph looks like. This is deeper than a flat list.

## Strengthened paste-ready text

```markdown
### 11.59 Capability ownership hierarchy

Every business capability has exactly ONE owning service. Sub-
capabilities may have their own services, but they are composed by the
parent — never called directly by controllers or Livewire.

#### Capability tree (v1)

```
Sales
├── InvoiceService           — create, submit, cancel, amend
│   ├── DocumentNumberService — generate sequential numbers
│   ├── PricingService        — validate price within range, calculate totals
│   │   ├── DiscountService   — apply max_discount, line-level discounts (v1.1)
│   │   └── TaxService        — compute VAT per tax template
│   ├── StockService          — decrement van stock, write movement
│   └── PdfService            — generate bilingual PDF with QR
├── ProformaService          — create, validate range, convert to invoice
│   └── PricingService        — validate price within rep range
├── PaymentService           — collect, allocate across invoices, cancel
│   ├── CashBoxService        — increment/decrement rep cash box
│   └── CustomerBalanceService — update customer balance (computed, not stored directly)
├── ReturnService            — create, restore stock, reduce balance, cancel
│   ├── StockService          — increment van stock, write movement
│   └── CustomerBalanceService — reduce customer balance
└── ExpenseService           — log, decrease cash box, cancel
    └── CashBoxService        — decrement

Inventory
├── StockService             — decrement, increment, transfer, balance, reconcile
│   └── (no sub-services — this is the leaf)
├── StockImportService       — import CSV, validate, log
│   └── StockService          — write imported quantities
├── StockReconciliationService — create reconciliation, approve, adjust
│   └── StockService          — write adjustment movement
├── BatchService             — create, upload COA, expiry check
└── GoodsInTransitService    — create, add landed cost, receive (full or partial), cancel
    ├── LandedCostService     — distribute costs proportionally
    └── StockService          — write transit_in movement on receipt

CRM / Field
├── VisitService             — open, confirm arrival (GPS), close, submit report
│   └── GpsService            — geofence check, distance calculation
├── WorkSessionService       — start, end, summary, mark missed visits
├── CustomerService          — submit for approval, approve, reject, duplicate check
├── RouteService             — assign customers, assign reps
└── VanTransferService       — request, accept, ship, receive, cancel
    └── StockService          — transfer between vans / in-transit warehouse

Purchasing
├── PurchaseRequestService   — submit, review, veto
├── SupplierQuotationService — compare, accept, reject
├── PurchaseOrderService     — create, submit, receive (partial), cancel
│   └── StockService          — write purchase movement on receipt
└── (landed costs via LandedCostService under GIT)

Financial
├── FiscalPeriodService      — isClosed, isLocked, assertOpen
├── ExchangeRateService      — convert, store rate on document
├── LandedCostService        — distribute across items by quantity ratio
└── CustomerBalanceService   — compute and update balance (called by Invoice/Payment/Return services)

Compliance
├── EtaIntegrationService    — submit, cancel, refresh token (Egypt)
├── ZatcaQrService            — encode TLV QR (Saudi, v2)
└── EInvoicingService         — strategy resolver: routes to ETA or ZATCA by company country

Operations
├── AlarmService             — raise, acknowledge, resolve
├── NotificationService      — send via database channel (extensible per §11.76)
├── ActivityLogService        — log mutations (called by other services)
├── DataMigrationService     — import from Odoo/Excel
└── ReportService            — daily, monthly, per-rep, stock, expiry, transit
```

#### Rules
1. **A controller or Livewire component calls a TOP-LEVEL service only.**
   It never calls a sub-service directly. Example: a Livewire component
   calls `InvoiceService::create()`, NOT `PricingService::validate()` or
   `StockService::decrement()`. The parent service orchestrates its
   sub-services.
2. **A parent service may call its sub-services.** `InvoiceService`
   calls `PricingService`, `StockService`, `DocumentNumberService`,
   `PdfService`. The dependency graph is acyclic.
3. **A sub-service may NOT call its parent.** `StockService` never
   calls `InvoiceService`. This prevents cycles.
4. **Cross-capability calls go through the parent.** If
   `ReturnService` needs to check stock, it calls `StockService`
   (a leaf, no cycle). If it needs to update balance, it calls
   `CustomerBalanceService` (a leaf). It does NOT call
   `InvoiceService`.
5. **One capability = one owner.** If you need to compute a price,
   you call `PricingService`. There is no other service that computes
   prices. If a new pricing rule is needed, it's a new
   `PriceRule` implementation (§11.76), not a new service.
6. **If a capability isn't in this tree, it doesn't exist in v1.** Do
   not create services for capabilities not listed here without an ADR.

#### Dependency graph (visual, no cycles)
```
InvoiceService → DocumentNumberService
InvoiceService → PricingService → TaxService
InvoiceService → StockService
InvoiceService → PdfService → EtaIntegrationService

PaymentService → CashBoxService
PaymentService → CustomerBalanceService

ReturnService → StockService
ReturnService → CustomerBalanceService

ExpenseService → CashBoxService

GoodsInTransitService → LandedCostService
GoodsInTransitService → StockService

VanTransferService → StockService

PurchaseOrderService → StockService

AlarmService ← (dispatched via events, not called directly)
NotificationService ← (dispatched via events)
ActivityLogService ← (called by services, never by controllers)
```

#### When this tree changes
- Adding a sub-service: add it under the parent in this tree, in the
  same commit. Create an ADR if the sub-service introduces a new
  architectural pattern.
- Adding a top-level service: requires an ADR + user approval. The
  service must own a capability not covered by any existing service.
- Removing a service: mark it deprecated in this tree, remove in a
  later phase after all callers are updated.
```

# Feedback on over-documentation (incorporated)

## Notification channels — trimmed
The stress test's §11.63 listed email, SMS, WhatsApp, push as channels
to define. Per user feedback: v1 defines only the `NotificationChannel`
interface, the `DatabaseChannel` implementation, and the extension
point (§11.76). No other channels are documented. Future channels are
added via the extension point, not by expanding the guide.

## Filament conventions — trimmed
The stress test's §11.69 had a full Resource/table/form/navigation
spec. Per user feedback: keep naming convention (one Resource per
model, `app/Filament/Resources/{Model}Resource.php`), navigation groups
(needed for bilingual labels), relation managers (needed for the child-
table pattern), and the Policy gate (needed for authorization). Remove
the column-by-column table spec and the form-section spec — those are
implementation details the AI can derive from the schema and the design
system.

## Middleware — trimmed
The stress test's §11.66 listed every middleware. Per user feedback:
keep only project-specific middleware (`SetActiveCompanyContext`,
`RequireNonRepRole`, `RequireRepRole`, `SetLocaleFromSession`, security
headers). Laravel's built-in middleware (StartSession, VerifyCsrfToken,
etc.) is not documented — the AI knows Laravel defaults.
