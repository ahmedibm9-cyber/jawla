# PWA, Frontend, Accessibility, and Performance Static Audit

**Audit date:** 2026-07-22  
**Scope:** Checklist sections 5, 7, 8, 11, 12, 13; checks 4.1, 4.4, 4.5, 17.3, 17.5, 17.6, and 17.7.  
**Method:** Static repository inspection only, as required by the investigation brief. No application, browser, build, test, scanner, database, or network execution was performed. Consequently, source and document observations are generally **grade B**. Runtime qualities such as actual installability, accessibility, browser support, Core Web Vitals, memory behavior, and printed output remain unverified even when their implementation looks plausible.

## Executive verdict

This slice is **not release-ready**. The static review found **20 Fail, 38 Partial, and 1 N/A** results across 59 requested checks. The most serious problems are an unsafe authenticated-response caching policy, an apparently undefined offline-sync Alpine controller, uncontrolled service-worker takeover, lack of trustworthy end-to-end/offline/accessibility gates, and a deterministic color-contrast failure in core interactive styling.

The existing automated browser suite cannot substantiate PWA readiness: the application deliberately skips service-worker registration under WebDriver (`resources/views/layouts/app.blade.php:98-105`), the browser suite is Chromium-only (`tests/Pest.php:10-18`), and the test named as a full-day walkthrough only navigates through pages and checks for JavaScript errors (`tests/Browser/FullDayWalkthroughTest.php:78-105`).

## P0 release blockers

### P0-1 — Authenticated and API responses can persist across logout or user/company changes

- **Impact:** A user on a shared device may receive another user's stale or sensitive response while offline or during a network failure. Stale money/stock data can also drive an incorrect business decision.
- **Evidence:** Navigation responses are cached without checking status, ownership, `Cache-Control`, or authentication state (`public/sw.js:32-45`). Every other GET—including `/api`/authenticated responses—is written to a shared, unbounded cache and later used as the offline fallback (`public/sw.js:70-79`). The cache has no user/company namespace, expiry, entry limit, logout purge, or allowlist. The IndexedDB outbox is likewise not scoped to a user/company (`resources/js/offline/outbox.js:6-19`, `resources/js/offline/outbox.js:46-56`). Story CG2.1 explicitly requires identity-scoped offline storage and clearing but remains planned (`bmad-output/stories/CG2.1.offline-data-model-and-indexeddb.story.md:3`, `bmad-output/stories/CG2.1.offline-data-model-and-indexeddb.story.md:19-25`).
- **Required fix:** Do not cache authenticated HTML/API responses by default. Use an explicit public-shell allowlist, honor non-cacheable headers, version and bound cache entries, scope any permitted offline data to authenticated user + company, and atomically purge Cache Storage and IndexedDB on logout/session invalidation.
- **Release proof:** On one device, exercise user A/company A, logout, user B/company B, then force offline. Cache Storage/IndexedDB inspection and UI assertions must prove that no A data, URL, response body, queue item, or derived total is visible to B.

### P0-2 — Offline queue UI references a controller that is absent from source and the committed bundle

- **Impact:** The queue screen may fail at Alpine initialization, display the false empty state, and make users believe financial/stock actions synced when they did not.
- **Evidence:** The view requires `x-data="jawlaSyncQueue"` (`resources/views/livewire/app/sync-queue.blade.php:7`) and can show “All synced” from its zero-valued initial state (`resources/views/livewire/app/sync-queue.blade.php:25-30`). A repository search found no JavaScript definition in `resources/js` or `public/build`; the only other occurrence is a test that asserts the literal string (`tests/Feature/RepFlowOfflineUxTest.php:144-149`). The actual client sync module exposes `window.jawlaSync`, not an Alpine controller (`resources/js/offline/sync.js:98-112`).
- **Required fix:** Implement and register the controller, bind it to real queue state and lifecycle events, represent pending/syncing/failed/conflict/synced states truthfully, and prevent “all synced” until the queue has been loaded successfully.
- **Release proof:** A real-browser test must enqueue an operation offline, reload, show the correct pending count, reconnect, observe one server commit, and transition to synced. It must fail if Alpine reports an expression/controller error.

### P0-3 — A new service worker takes control immediately without safe update coordination

- **Impact:** Multiple open tabs or an in-progress sale can move to a mixed old/new asset or data state; a bad worker can take over immediately without a user-controlled recovery path.
- **Evidence:** Install calls `skipWaiting()` immediately (`public/sw.js:5-11`); activation deletes every prior cache and calls `clients.claim()` (`public/sw.js:15-25`). There is no waiting-version prompt, unsaved-work/outbox guard, schema handshake, rollback/version UI, or client reload protocol. Registration errors are swallowed (`resources/js/pwa-register.js:1-4`; `resources/views/layouts/app.blade.php:98-107`).
- **Required fix:** Adopt a staged update protocol: keep the new worker waiting, notify clients of the version, block activation during critical/unsynced work, activate after explicit safe consent, coordinate reload across tabs, and retain a compatible rollback path.
- **Release proof:** Run old and new builds with two tabs, one active financial draft and one queued offline action. Demonstrate no data loss, no mixed-version execution, deterministic activation, and recovery from a deliberately faulty update.

### P0-4 — The acceptance suite does not exercise the critical journeys or PWA runtime

- **Impact:** Release gates can pass while sales, payments, returns, offline sync, installation, updates, cross-tenant isolation, keyboard access, or mobile layouts are broken.
- **Evidence:** The production guide requires a full rep-day flow and an admin stock flow (`docs/Jawla_Production_Build_Guide.md:181`), but the named full-day test only visits pages (`tests/Browser/FullDayWalkthroughTest.php:78-105`). Service workers are disabled under WebDriver (`resources/views/layouts/app.blade.php:98-105`). Only Chromium is configured (`tests/Pest.php:10-18`); there is no Playwright configuration, browser matrix, visual baseline, or accessibility runner in `package.json:5-24`. Stories B8.1, B8.2, and B8.4 still contain unchecked acceptance criteria (`bmad-output/stories/B8.1.playwright-setup-ci.story.md:20-35`, `bmad-output/stories/B8.2.am1-am9-walkthrough-test.story.md:20-46`, `bmad-output/stories/B8.4.b0-ui-state-regression-suite.story.md:20-39`).
- **Required fix:** Establish a release-blocking Playwright matrix with real service-worker coverage, actual rep/admin mutations and assertions, tenant/role denial, mobile viewports, offline/update/session interruption, trace/video artifacts, accessibility scans, and visual comparisons.
- **Release proof:** CI must fail on a deliberately broken sale, missing sync controller, inaccessible control, service-worker caching regression, and RTL visual regression.

### P0-5 — Core brand styling fails the project's own contrast requirement

- **Impact:** Primary controls, outline controls, and focus indication can be unreadable or difficult to perceive; this is a release-blocking accessibility barrier.
- **Evidence:** Brand green is `#6DB83B` (`resources/css/app.css:22`) and is paired with white for primary controls (`resources/css/app.css:264-276`) and used for focus/outline styling (`resources/css/app.css:198-206`, `resources/css/app.css:292-305`). Its contrast against white is approximately 2.4:1, below the documented 4.5:1 text and 3:1 UI thresholds. The design-system claim that all ratios meet WCAG AA is therefore contradicted (`docs/DESIGN_SYSTEM.md:111-117`). No automated or retained manual accessibility audit exists (`package.json:5-24`).
- **Required fix:** Replace or contextualize the color tokens so normal text reaches 4.5:1 and non-text/focus indicators reach 3:1 in all states and themes; do not rely on color alone.
- **Release proof:** Retain automated contrast results plus manual high-contrast, forced-colors, keyboard-focus, and representative Arabic/English screen evidence.

## P1 findings

- **P1 — Offline durability and recovery are incomplete.** Queue records have no age/size/quota policy or user/company scope (`resources/js/offline/outbox.js:6-19`, `resources/js/offline/outbox.js:46-69`); processing is not proven FIFO, retry is immediate without backoff, and failures are silent (`resources/js/offline/sync.js:31-74`, `resources/js/offline/sync.js:84-95`).
- **P1 — Initial-load and bundle governance are absent.** Sentry, Replay, Leaflet CSS, offline sync, autocomplete, and Bluetooth paths are loaded from global entries (`resources/js/app.js:1-18`, `resources/css/app.css:1-2`); the Vite manifest exposes only the main CSS/JS entries (`public/build/manifest.json:146-163`), while no bundle/CWV budget is defined (`package.json:5-24`).
- **P1 — Media can become a bandwidth and storage burden.** Uploads allow 5 MB and are stored as originals (`app/Livewire/App/PhotoCapture.php:28-43`, `app/Services/PhotoService.php:32-46`); rendered images lack dimensions and lazy loading (`resources/views/livewire/app/photo-capture.blade.php:22-35`).
- **P1 — Semantic and keyboard defects are present.** Most page headers render an `h2` despite the one-H1 requirement (`resources/views/components/page-header.blade.php:3-14`; `docs/DESIGN_SYSTEM.md:40-44`), and the home visit card nests an anchor inside a button (`resources/views/livewire/app/home.blade.php:52-70`).
- **P1 — Platform readiness is unproven.** There is no supported browser/OS/device matrix, iOS install/standalone coverage, mobile keyboard/safe-area validation, or non-Chromium CI (`tests/Pest.php:10-18`; `package.json:5-24`).
- **P1 — Operational documents disagree about runtime behavior.** Deployment says `route:cache` is disabled, while Railway enables it (`docs/DEPLOYMENT.md:37-39`; `railway.toml:1-3`). Deployment requires a Redis queue worker for offline replays while rollback says no worker is required (`docs/DEPLOYMENT.md:41-53`; `docs/ROLLBACK.md:34-37`).

## Concrete verification plan

1. **Secure offline identity boundary:** On a shared browser profile, create data and queued operations as user A/company A; logout; sign in as B/company B; cut the network; inspect Cache Storage and IndexedDB and assert no A content, keys, totals, URLs, or operations remain. Repeat after session expiry and permission revocation.
2. **Real service-worker journey:** Use a dedicated browser suite that does not take the `navigator.webdriver` bypass. Install from a clean profile, load online, go offline, navigate supported routes, enqueue each permitted operation, reload/kill the tab, reconnect, and assert exactly-once server effects plus truthful UI states.
3. **Update safety:** Keep two tabs on build N with a financial draft and queued operation; deploy build N+1; verify waiting/version UI, safe deferral, coordinated activation/reload, schema compatibility, and no loss. Repeat with a deliberately faulty worker and prove rollback/recovery.
4. **Failure matrix:** For sync/install/navigation test timeout, DNS/captive-like failure, slow/flapping network, 401, 403, 419, 422, 429/Retry-After, 500, malformed JSON, storage denied/full/corrupt, permission deny/revoke, and duplicate requests. Every case needs bilingual next steps and must never display false success.
5. **Critical E2E:** Execute the exact guide workflow: login → start work → route → visit with mocked permission states → sell three items → collect → return → end day → verify admin totals; and admin create product → load van → verify stock. Add role/tenant denial and transaction failure paths.
6. **Browser/device matrix:** Run current stable Chromium, Firefox, and WebKit plus supported Android/iOS devices in browser and installed/standalone modes. Cover portrait/landscape, keyboard open, safe areas, deep links, back/refresh, expired session, camera, location, Bluetooth fallback, and reinstall.
7. **Accessibility gate:** Run automated WCAG checks on every representative state, then manually complete keyboard-only, NVDA+Firefox/Chrome, VoiceOver+Safari, 200%/400% zoom, text spacing, forced colors/high contrast, reduced motion, touch targets, Arabic/English and mixed bidi. Retain results and linked defects.
8. **Visual regression:** Approve deterministic Arabic/English baselines for phone/tablet/desktop, light/dark, portrait/landscape, loading/empty/error/success/validation/modal/toast/offline/update states. CI should fail outside a reviewed threshold.
9. **Performance baseline:** Against the current production-like Docker/FPM build, collect cold/warm mobile Lighthouse/Web Vitals, bundle/font/image bytes, request count, TTFB/API p95/p99, offline replay load, low-end CPU long tasks/INP, and long-session heap. Attach budgets and fail CI on regression.
10. **PDF/print certification:** Generate invoices/returns with Arabic+English, mixed bidi, long names, missing/large signatures, QR, and 1/10/100+ items. Verify embedded fonts, page breaks, no clipping, QR scans, A4/thermal/device output, filenames/content disposition and unauthorized access.
11. **Search/i18n/time boundaries:** Use Arabic variants/diacritics, English case/accents, emoji/mixed bidi, whitespace/long input, empty/huge datasets, timezone midnight/month/year/DST and client clock skew. Verify stable sort, pagination, locale formatting and query targets.
12. **Release no-go criteria:** Do not release until P0-1 through P0-5 have linked fixes and retained runtime evidence; all CG2 acceptance is resolved if offline is in scope; critical E2E passes with a real SW; and accessibility/performance/browser matrices have approved results or explicit, time-bounded risk acceptance.

## Evidence limitations

No grade A runtime claim is made in this report. Passing source patterns (for example, a valid-looking manifest, media-query rules, or idempotency tests) do not prove installed-app, real-device, assistive-technology, network, print, or production performance behavior. Conversely, several failures are deterministic from static source—especially unsafe cache policy, absent queue-controller definition, test bypass of the SW, and the documented color pairing—but remain grade B under the investigation brief's evidence rules.
