## Story

**As a** sales rep on a weak connection,
**I want** every tap to either visibly succeed, visibly fail, or visibly queue — and retries to never duplicate a sale or payment,
**so that** the app stops "hanging" on me and I can trust what got saved.

---

## Context (from the investigation — do not rediscover)

- **This is the owner's reported symptom** ("actions fail or hang"). Root causes identified:
  1. No global Livewire request-failure handler anywhere (`resources/js/app.js`) — a timed-out/failed/419 request leaves the screen frozen with zero feedback (E5).
  2. The **online** submit paths (SalesFlow, CollectPayment, LogReturn, LogExpense, VisitFlow report) carry no idempotency key — a commit whose response was lost + a natural retry = duplicate write (E3.4). The **offline** path already solved this: client keys + `sync_receipts` unique `(company_id, idempotency_key)` + server `applied|duplicate` reconciliation (E7 — reuse it, don't rebuild it).
  3. `window.jawlaSync.enqueue(...)` is called unguarded in the confirm buttons (sales-flow.blade.php:197 et al.) — if the JS bundle failed to load, the offline confirm tap is a silent no-op (E6).
  4. `navigator.onLine === true` with no real internet (captive portal, dead 3G) sends the online branch into a doomed request instead of the outbox.

## Acceptance Criteria

1. **Online idempotency:** each confirm-tap generates a client key (same generator the outbox uses); the Livewire submit passes it through, and the services record it in `sync_receipts` inside the same transaction. Replaying the same key returns the original result (no second invoice/payment/return/expense/visit-report). Feature tests: same key twice → one record; distinct keys → two.
2. **Failure is visible:** a global Livewire hook (registered once in `app.js`) catches failed commits (network error, timeout, 419, 5xx) and shows a bilingual toast: what failed + "check the sync queue / try again". 419 additionally prompts re-login. No rep screen can fail silently anymore.
3. **Dead-bundle guard:** every `window.jawlaSync` call site checks existence first; if missing, show a bilingual error instead of doing nothing.
4. **Doomed-online fallback:** if the online submit fails with a network-level error, offer one-tap "save offline instead" which enqueues to the outbox with the SAME idempotency key already generated for the attempt — so even "server actually committed but response was lost" resolves as `duplicate`, never a double write.
5. **Visit report duplicate guard:** `VisitReportService::submit()` refuses a second report for an already-closed visit (bilingual error), covering online double-taps the same way sync dedupe covers replays.
6. Full suite green; RTL + bilingual strings for every new user-facing message.

## Dev Notes

- `sync_receipts` and `SyncService` are the single source of idempotency truth for BOTH paths — do not introduce a parallel mechanism.
- Keep the failure toast dumb and global; per-page custom handling stays out of scope.
- After this story, re-test the owner's "hang" complaint on a throttled connection (DevTools offline/slow-3G) across: sale, payment, return, expense, visit report.
