### Current Problem (Evidence from Investigation)

Issues:
1. Migration 1 CHECK constraint has 4 values; Migration 2 tries to replace with 5 DIFFERENT values
2. DROP CONSTRAINT IF EXISTS purchase_requests_status_check uses hardcoded name -- PostgreSQL auto-generates constraint names (typically table_column_check but not guaranteed)
3. Old values (reviewed_by_sales, approved) are NOT in new enum -- existing rows would violate new constraint

### Recommended Fix

Option A (Simplest): Update Migration 1 to have final 5 values, remove constraint logic from Migration 2 entirely.

```php
// Migration 1 - line 21
->enum('status', ['pending', 'sales_approved', 'purchasing_approved', 'rejected_by_sales', 'rejected_by_purchasing'])->default('pending');
```

```php
// Migration 2 - REMOVE lines 12-13 entirely
// Keep only the Schema::table column additions
```

Option B: Migration 1 creates column without enum CHECK; Migration 2 adds named constraint with CREATE CONSTRAINT ....
