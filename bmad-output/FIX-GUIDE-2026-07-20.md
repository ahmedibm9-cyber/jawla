## Executor rules (non-negotiable)

1. **CLAUDE.md governs.** In particular: all money/stock mutations stay inside `DB::transaction()` in a Service; stock changes ONLY via `StockService`; `$fillable` only; every user-facing string bilingual AR/EN in `lang/ar/app.php` + `lang/en/app.php`; RTL must keep working; pagination on every list; no new composer/npm packages — everything below is achievable with what is installed.
2. **After every phase:** `vendor/bin/pint --dirty` → `php artisan test` (must be 0 failures) → commit `fix: phase N — <title>` (or `feat:` where noted). Never batch phases into one commit.
3. **Failure-path tests are mandatory** for every money/stock change (CLAUDE.md). Where this guide says "Test:", write it as a Pest Feature test unless it says Unit.
4. Where this guide prescribes a pattern, **use the prescribed pattern even if you'd prefer another** — consistency with the existing codebase idiom was chosen deliberately.
5. If something in the code contradicts this guide (drifted line numbers, renamed files), trust the code, keep the _intent_, and note the drift in the commit message. Line numbers below are from `ef4bab9`.
6. Do NOT: add expense/cash-box floor checks (owner deferred), build a below-min price approval flow (owner rejected), touch `docs/BUSINESS_RULES.md` / `docs/SECURITY.md`, or start Phase 9 (MFA) without owner confirmation.

## Phase 1 — SW-1: service worker stale-cache + logged-out access (High) — DO FIRST

**Problem.** `public/sw.js` serves navigations **cache-first, forever**: after any deploy, reps keep the old HTML/JS (broken screens, 419s, "hangs"); after logout, cached authenticated pages still render with customer data and no auth check.

**Fix, exactly this way:**

1. In `public/sw.js`:
   - Bump `const CACHE = "jawla-shell-v5"` → `"jawla-shell-v6"` (forces every existing device to drop poisoned caches on next visit — this is the one-time recovery for phones already in the field).
   - **Navigation branch → network-first.** Replace the current cache-first navigation handler with: try `fetch(e.request)`; on success, put a clone into the cache and return it; on network failure, return `caches.match(e.request)`, falling back to `caches.match("/offline")`. Keep the existing static-asset branch cache-first (Vite hashes make those immutable) and keep the API/other branch as-is **except** see step 3.
   - **Add a message listener** for cache purge:
     ```js
     self.addEventListener("message", (e) => {
       if (e.data === "purge-pages") {
         caches.delete(CACHE);
       }
     });
     ```
2. Purge on logout/expiry: in `resources/views/layouts/app.blade.php`, the guest login view is rendered through `LoginController::create` using the same layout. Add a tiny inline script that runs **only when no authenticated user** (wrap in `@guest ... @endguest`):
   ```js
   navigator.serviceWorker?.controller?.postMessage("purge-pages");
   ```
   Rationale: anyone seeing the login page (logout, session expiry, revoked user) triggers the purge — no logout-handler plumbing needed and it also covers expiry.
3. Stop caching sensitive non-page GETs: in `app/Http/Controllers/App/PdfController.php::download()`, add `'Cache-Control' => 'no-store'` to the response headers. In `sw.js`'s API/other branch, skip caching when the response carries `no-store` (check `r.headers.get("Cache-Control")?.includes("no-store")` before `c.put`).

**Verify:** (a) Pest: PDF response has `no-store` header. (b) Manual/browser: load `/app`, stop the server → reload still works from cache fallback; restart server, change a blade string, reload → new string appears on FIRST reload (network-first). (c) Log out → DevTools Application → Cache Storage: page cache gone; with DevTools offline, `/app/customers` no longer renders data, falls to `/offline`.

**Commit:** `fix: phase 1 — service worker network-first navigations, purge on logout, no-store PDFs (SW-1)`

## Phase 2 — Story 08.1: concurrency & money integrity (High)

Full ACs in `bmad-output/stories/08.1.concurrency-hardening.story.md`. Implementation prescriptions:

### 2a. Sale double-submit

`app/Livewire/App/SalesFlow.php::submit()`:

- First line: `if ($this->step !== 'cart') { return; }`
- After success (where `step = 'done'` is set): also `$this->reset(['cart', 'customerId'])` — but NOTE: `createdInvoiceId`, `successMessage`, `invoicePrintPayload` must survive for the done-screen, so reset only those two, then `recalcCart()`.
  **Test:** mount, fill cart, call `submit()` twice → `Invoice::count() === 1`, stock decremented once, balance incremented once.

### 2b. Cancel-once everywhere — use the in-repo idiom

The canonical pattern is `CashReconciliationService::review()` (CashReconciliationService.php:53-73): **inside** the transaction, re-fetch `->whereKey($model->getKey())->lockForUpdate()->firstOrFail()`, re-check state on the fresh row, `throw_if` not permitted, then act on `$fresh` only. Apply to:

| File                                  | Method(s)                                                                                                                                                                               | Fresh-row guard to enforce                                                                                                                                            |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `app/Services/InvoiceService.php`     | `cancel()`, `amend()` (both funnel into `cancelWithoutTransaction()` — put the lock+guard at the top of `cancelWithoutTransaction`, which already runs inside the caller's transaction) | `status !== Cancelled` (throw bilingual "already cancelled"); also read `paid_amount`/`total` from the **locked** row for the balance reversal (fixes the stale-read) |
| `app/Services/ReturnService.php`      | `cancel()`                                                                                                                                                                              | `status !== 'cancelled'`                                                                                                                                              |
| `app/Services/PaymentService.php`     | `cancel()`                                                                                                                                                                              | `cancelled_at === null`                                                                                                                                               |
| `app/Services/ExpenseService.php`     | `cancel()`                                                                                                                                                                              | `cancelled_at === null`                                                                                                                                               |
| `app/Services/VanTransferService.php` | `ship()`, `receive()`, `reject()`, `cancel()`                                                                                                                                           | replace `findOrFail` + status check with `lockForUpdate()->findOrFail` then the existing status `throw_if`s                                                           |

Add translation keys (suggest `app.already_cancelled`, `app.transfer_state_changed`) in both lang files.
**Tests (per service):** second cancel throws AND stock/cashbox/customer-balance identical to post-first-cancel values. Van transfer: `ship()` twice → stock moved exactly once, second throws.

### 2c. Payment guards + overpayment-as-credit (owner decision)

`app/Services/PaymentService.php::collect()`:

- Load the invoice with `lockForUpdate()` when `$invoiceId` present.
- `abort_if` invoice status is `Cancelled` or `Draft` (422, bilingual).
- Overpayment split: `$applied = min($amount, (float)$fresh->remaining_amount)`; increment `paid_amount` by `$applied`, decrement `remaining_amount` by `$applied` (never below 0); the **full** `$amount` still decrements customer balance (surplus = customer credit) and the full amount goes to the cash box. Status transitions unchanged otherwise.
  **Tests:** exact pay → `Paid`, remaining 0; overpay by 50 → `Paid`, remaining 0, customer balance = old − total − 50; pay on cancelled → 422, nothing mutated.

### 2d. Stock-backed sales always (owner decision)

In `InvoiceService::create()`/`submit()`/`cancelWithoutTransaction()` and `ReturnService::create()`/`cancel()`: replace the silent `if ($vanWarehouse)` skip with `throw_if(! $vanWarehouse, ...)` using a new bilingual message (`app.van_stock_not_configured`: "مخزون السيارة غير مُعد — تواصل مع مديرك / Your van stock is not set up — contact your manager"). Exception type: reuse `App\Exceptions\Domain\InsufficientStockException`'s pattern — create a sibling `DomainException` if none fits.
**Tests:** rep without van warehouse: sale throws, **zero** rows created (full rollback); same for return.

### 2e. Proforma converts once

`InvoiceService::create()` (:106-110): change to a guarded conditional update and check affected rows:

```php
$updated = ProformaInvoice::where('id', $data['proforma_invoice_id'])
    ->where('status', '!=', 'converted_to_invoice')
    ->update(['status' => 'converted_to_invoice']);
throw_if($updated === 0, /* bilingual: already converted */);
```

**Test:** two `create()` calls with the same proforma id → one invoice, second throws.

### 2f. First-sale stock-row race + reconcile lock

`app/Services/StockService.php`:

- In `move()`: wrap `Stock::create` in try/catch `UniqueConstraintViolationException` → on catch, re-run the `lockForUpdate()` fetch and continue (mirror `NumberSequenceService::generate()`'s fallback shape at NumberSequenceService.php:20-36).
- In `reconcile()`: fetch the stock row with `lockForUpdate()` before computing `balance()`/difference (use `firstOrCreate` then re-fetch locked, or lock the existing row; keep the movement write identical).
  **Test (Unit ok):** simulate the unique-violation path by pre-creating the row between fetch and create (mock or sequential arrangement) → `move()` succeeds without throwing.

**Commit:** `fix: phase 2 — money-integrity hardening: cancel-once locks, payment guards, stock-backed sales (08.1)`

## Phase 3 — Story 08.2: online idempotency + visible failures (High)

Full ACs in `08.2.rep-action-reliability.story.md`. Prescriptions:

### 3a. One shared idempotency helper

Create `app/Support/IdempotentWrite.php`:

```php
final class IdempotentWrite
{
    /** Runs $write exactly once per (companyId, key). Returns the stored result on replay. */
    public static function run(int $companyId, int $userId, string $key, string $type, \Closure $write): array
    // inside: DB::transaction → try SyncReceipt::create([...key, type, company_id, user_id, status:'applied', result:...])
    // catch UniqueConstraintViolationException → fetch existing receipt, return its stored result with 'duplicate' => true
    // The receipt INSERT and the $write() happen in the SAME transaction so a rollback also releases the key.
```

Model/table already exist: `sync_receipts`, unique `(company_id, idempotency_key)` — reuse them; check `App\Services\Sync\SyncService` first and extract/delegate so BOTH paths share one code path (do not duplicate the receipt logic; refactor SyncService to call the helper if its shape allows, otherwise have the helper mirror its exact semantics including the stored-result JSON shape).

### 3b. Thread keys through the four online flows

- Blade confirm buttons (sales-flow, collect-payment, log-return, log-expense): generate the key at tap time in Alpine — `$wire.submit(crypto.randomUUID())` — and in the offline branch pass the **same** key into `window.jawlaSync.enqueue(type, payload, key)` (extend `enqueue` in `resources/js/offline/sync.js` + `outbox.js` to accept an explicit key; today the outbox id is the key — keep that as fallback).
- Livewire `submit(?string $idempotencyKey = null)` methods wrap their service call in `IdempotentWrite::run(...)` when a key is present (null key = legacy behavior, still works).
  **Tests:** call `submit($key)` twice with same key → one invoice/payment, second returns the first's result; distinct keys → two records; key rolled back on validation failure can be reused.

### 3c. Global Livewire failure feedback

In `resources/js/app.js`, register once:

```js
document.addEventListener("livewire:init", () => {
  Livewire.hook("request", ({ fail }) => {
    fail(({ status, preventDefault }) => {
      if (status === 419) {
        window.dispatchEvent(new CustomEvent("jawla-session-expired"));
        preventDefault();
      } else if (status === 0 || status >= 500) {
        window.dispatchEvent(new CustomEvent("jawla-request-failed"));
        preventDefault();
      }
    });
  });
});
```

In `layouts/app.blade.php`, add a small fixed-position Alpine toast listening for those two events: `jawla-request-failed` → bilingual "لم يتم الحفظ — تحقق من الاتصال وحاول مجددًا / Not saved — check your connection and try again" with a dismiss button; `jawla-session-expired` → message + link to `/app/login`. Bilingual strings via `__('app.request_failed')`, `__('app.session_expired')`.

### 3d. Guards

- Every `window.jawlaSync` call site: `if (!window.jawlaSync) { /* show the same failure toast */ return; }`.
- `app/Services/VisitReportService.php::submit()`: inside the transaction, `throw_if($visit->reports()->exists() || $visit->status === 'closed', ...)` (add the `reports()` hasMany if missing) — bilingual "report already submitted". **Test:** double submit → one report.

**Commit:** `feat: phase 3 — online idempotency keys, global failure toast, sync guards (08.2)`
